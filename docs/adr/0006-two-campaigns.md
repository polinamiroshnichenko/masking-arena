# ADR-0006: Две кампании — маскирование и восстановление выращиваются отдельно

- Статус: proposed (принимается при подготовке, до заморозки условий)
- Дата: 2026-11-06

## Контекст
Барьер решает две почти независимые подзадачи. **Маскирование** — найти ПДн и заменить метками: регулярки, контекст, словари, NER. **Восстановление** — вернуть значения в ответ модели в нужном падеже и узнать искажённые метки: нормализация, морфология. Общего кода у них почти нет.

В одной кампании score — это произведение `H·φ(P) · A` (ADR-0003). Отсюда две проблемы:
- **Слабый сигнал.** Улучшение одной части масштабируется качеством другой: при A = 0.44 рост H·φ на 0.1 даёт только +0.044 к score.
- **Неразборчивая история.** Кривая эволюции смешивает два процесса, и скачок нельзя однозначно приписать детектору или склонению. А разбор эволюции (B-6) — основа защиты.

## Решение
Две кампании на одних данных, одном разбиении и одном замороженном пакете метрики.

| | Кампания `mask` | Кампания `unmask` |
|---|---|---|
| Примеры | только `task = mask` из train/public/private | только `task = unmask` |
| Размеры train / public / private | 1200 / 420 / 630 | 500 / 180 / 270 |
| Метрика | тот же пакет; на наборе без unmask агрегатор даёт `H · φ(P)` | тот же пакет; на наборе без mask агрегатор даёт `A` |
| Стартовый кандидат | baseline (регулярки) | baseline (замена без склонения) |
| Лимит решений (предварительно) | 90 | 30 |
| Финал | K = 4, N = 2 | K = 3, N = 1 |

Отдельный пакет метрики не нужен: `aggregate.py` опускает множитель отсутствующего типа примеров (ADR-0003, тесты `test_aggregate_*_only`). Выделение примеров одного типа — `tools/select_task.py`.

**Связка.** После обеих финализаций лучший маскировщик и лучший восстановитель объединяются в одно решение — это и есть навык. Оператор один раз прогоняет связку и baseline на полном private (mask + unmask) полной формулой `H·φ·A`. Этот прогон — проверка вне кампаний: после него ничего не дорабатывается. В отчёте он описан отдельно от результатов кампаний.

## Альтернативы
- **Одна кампания с произведением (прежний план).** Меньше подготовки и одна private-серия, но сигнал слабее и историю трудно разобрать. Плюс в том, что связка оценивается на private внутри кампании.
- **Одна кампания с суммой компонент вместо произведения.** Убирает масштабирование, но позволяет игнорировать одну подзадачу (ADR-0003) и не решает проблему смешанной истории.
- **Две кампании с разными пакетами метрики.** Чище по форме, но две заморозки и две метрики, которые нужно держать согласованными. Один пакет даёт то же поведение.
- **Сначала mask, затем unmask, начиная от его победителя.** Последовательность не нужна: подзадачи не зависят от кода друг друга.

## Последствия
- Две кривые, два дерева и два AUC в `docs/evolution.md`. Можно сравнить, где эволюция дала больше и как быстро вышла на плато.
- Подготовка вдвое больше: два журнала, две private-серии, два ревью. Общий лимит 120 решений сохраняется, но делится 90 / 30. Окончательно — после пилота.
- **Точка связи не оценивается ни в одной кампании:** маскировщик должен сохранить каноническую (именительную) форму значения, которую потом использует восстановитель. Проверяется в тестах навыка (B-8.3) сквозным сценарием «документ → маска → ответ модели → восстановление». Кандидат в метрику v2.
- Требование B-5.1 («одна полная кампания») выполняется с запасом. Бонус B-5.3 (повтор кампании с другими условиями) — это другое, две подзадачи его не заменяют.
